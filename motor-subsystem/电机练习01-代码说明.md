## 2. 先补三个概念

你只做到 Getting Started §4（LED 闪烁），所以下面三件事可能是新的。不搞清楚这三件，代码你只能"看着像对"。

### 2.1 三个文件的分工

```
DemonstrationTest.ino   顶层。setup() 开机跑一次，loop() 开机后反复跑，永不结束
    ↓ 调用
Controller.h            声明（相当于书的目录页）：有什么函数、什么变量、什么常量
Controller.cpp          实现（相当于书的正文）：函数具体怎么干活
```

为什么拆开？因为 `.h` 是给别人看的"接口清单"——你只看 `Controller.h` 就知道这个类能做什么，不用读几千行实现。Arduino 编译时会自动把同目录下的 `.cpp` 都编进去，你不用手动 `#include` 它们。

**注意**：`.ino` 里 `#include "Controller.h"` 之后，才能用 `Controller_c` 这个名字。

### 2.2 class 是什么，`public` / `private` 是什么

```cpp
class Controller_c {
  public:
    OdometryModel_c odometry;
    int call_count;      // ← 我加的
  private:
    uint8_t signal;
    void runLineFollower(...);
};
```

- **class 就是一个打包盒**：把"变量"和"函数"捆在一起，起个名字叫 `Controller_c`。
- `.ino` 第 18 行 `Controller_c controller;` 用这个盒子造了一个**全局实例**，名字叫 `controller`。它从开机一直活到断电。
- `controller.update(robot, server)` 里的那个**点号**，意思是"用 `controller` 这个盒子里的 `update` 函数"。和 `robot.setMotorPWM(...)` 的点号是同一个用法。
- **`public` / `private` 只是给"人"看的约定**，区分对外接口和内部零件。`public` 里面的东西外面能碰，`private` 里面的只有这个类自己的函数能碰。编译器会强制这条规矩，所以写错了会报错——这是好事，等于帮你抓 bug。

> **本练习最关键的一点**：`call_count` 这类变量叫**类变量**（定义在函数外面）。它和普通局部变量的区别是——**函数每次退出后它还记得自己的值**。局部变量一出函数就被清了，没法用来"数 3 秒里被调用了几次"。这就是练习要你把 `call_count` 定义在 `Controller.h` 而不是函数里面的原因。

### 2.3 10ms 契约，以及为什么禁用 `delay()`

`Controller.cpp` 的 `update()` 开头有这么一段：

```cpp
if (!update_timer.isReady(now)) {
    return;              // ← 没到 10ms，直接结束，什么都不干
}
update_timer.resetTimer(now);
```

`update_timer` 是 `TaskTimer_c` 类型，它保证 **`update()` 里真正的活儿每 10ms 才执行一次**（100 次/秒）。这有两个后果：

1. **别把间隔改小于 10ms**。课程原话：Pololu 3Pi+ 主控要时间处理自己的传感器、电机、里程计和 I2C 应答，压到 10ms 以下会挤爆它。
2. **本练习的 3 秒，是在"数次数"而不是"看时钟"**：10ms 一次 × 300 次 = 3000ms = 3 秒。

**为什么 `delay()` 是禁术**：`delay(500)` 会让整个 `loop()` 原地卡死 500ms。这期间 `server.update()` 不跑、按钮不检测、10ms 节奏全乱。`delay()` 只适合 `setup()` 里或纯演示，一旦进入有实时性要求的循环就是灾难。

**非阻塞的正确姿势**：不等，只数。

```cpp
// 每个 10ms 被调用一次；不阻塞任何人，只是记账
call_count = call_count + 1;
if (call_count >= 300) { ...该收尾了... }
```

这就是练习页面反复强调 "non-blocking" 的意思：**函数每次进来干一点点活就立刻返回**，靠类变量记住进度。

## 3. 逐处讲解

### 3.1 `DemonstrationTest.ino`

```cpp
void loop() {
  server.update();                      // 维持可选的 WiFi/TCP 遥测连接
  controller.update(robot, server);     // 控制器转一圈
}
```

`server.update()` 有没有客户端连上来都无所谓，不连就空转。`controller.update()` 内部自己管 10ms 节流和按钮检测，你不需要在外面加任何东西。

**第 29 行——队名已设为 `"119"`**：

```cpp
robot.initialise("119");
```

这条**不是可选项**。课程介绍里写明：机器人预装了一层 **middleware（中间件）**，它会给电机和传感器**人为加上一些可测量的特性**（死区、饱和、非线性……就是你后面练习 3–6 要测的东西），而且**按学生单独配置**——所以你测出来的结果和别人不一样，AI 也猜不到。

- 填了队名 → 启用你那套 middleware
- 不填，用 `robot.initialise()` → **裸基线，没有 middleware**，你的测量结果不属于课程预期

> 队名只写进 `DemonstrationTest` 这一份。`StampC3_Template` 保持原样（`robot.initialise();`），它是"原版参考"，用来对照用的。的那一套

### 3.2 `Controller.h`

**三个类变量**（27–31 行，放在 `public:` 下面，紧跟着 `odometry`）：

```cpp
int call_count;      // 数 update() 调用了几次 —— 用来计 3 秒
float ramp_pwm;      // 当前要给电机的 PWM 大小
int ramp_count;      // 子计数器：数到 10 就改一次 ramp_pwm
```

`float` 而不是 `int`：PWM 一会儿要做加减和除法，小数部分有用。`setMotorPWM()` 收的也是 `float`。

**四个常量**（52–61 行，跟在 `RECOVERY_RIGHT_PWM` 后面）：

| 常量 | 值 | 含义 | 想调就改这里 |
|---|---|---|---|
| `TEST_DURATION_CALLS` | 300 | 测试总长（10ms × 300 = 3 秒） | 改测试时长 |
| `RAMP_STEP_INTERVAL` | 10 | 每 10 次调用（100ms）改一次 PWM | 改斜坡的"台阶"宽度 |
| `RAMP_PWM_STEP` | 4 | 每次改动的幅度 | 改斜坡陡峭程度 |
| `MAX_RAMP_PWM` | 60 | PWM 上限 | 改最高转速 |

**`MAX_RAMP_PWM = 60` 是我替你定的保守值，你可以也应该自己判断。** 依据：模板自己的搜索转向常量用 ±35，middleware 的硬上限是 ±200。练习原文要求 "Choose conservative PWM commands with your team; do not ask AI to choose supposedly safe values for your robot." —— 所以看完这行说明，**自己拍板**。

**函数原型**（127 行）：

```cpp
void motorStartStopTest(Robot_c &robot, unsigned long now);
```

定义在 `private:` 区，紧接着 `runLineFollower`。原因：它和 `runLineFollower` 一样，是只被 `update()` 内部调用的例程，不对外。注意原型**没有 `Controller_c::` 前缀，也没有 `{ }`**——这就是"声明"和"实现"的区别，和书的目录页 vs 正文一个道理。

### 3.3 `Controller.cpp`

**① 常量定义（11–14 行）**

```cpp
const int Controller_c::TEST_DURATION_CALLS;
```

`.h` 里已经写了值（`= 300`），这里为什么又写一遍？这是 C++ 的历史包袱：类里的 `static` 成员在被"取地址/绑定引用"时需要一份类外定义。模板里原有的 `BASE_PWM` 等常量全都这么写了一遍，我保持一致。**照抄即可，不写在某些情况下会链接报错。**

**② `reset()` 初始化（29–31 行）**

```cpp
call_count = 0;
ramp_pwm = 0.0f;
ramp_count = 0;
```

`reset()` 是"软复位"。`Controller_c` 的构造函数里已经调过它一次（第 15 行），所以开机时这三个变量就是 0。**但练习要求你在 `reset()` 里也写一遍**——因为测试跑完后我们要靠 `setSignal(0)` → `reset()` 把状态清零，好让按钮能再来一轮。

**③ `motorStartStopTest()` 本体（153–189 行）**

```cpp
void Controller_c::motorStartStopTest(Robot_c &robot, unsigned long now) {

  if (call_count >= TEST_DURATION_CALLS) {     // ← 已经跑满 300 次
    robot.setMotorPWM(0, 0);                   //   显式把两个轮子置 0
    setSignal(0);                              //   解除启动信号，允许再按按钮
    return;                                    //   本次到此为止
  }

  call_count = call_count + 1;                 // ← 记一次账

  ramp_count = ramp_count + 1;                 // ← 子计数器
  if (ramp_count >= RAMP_STEP_INTERVAL) {      //   满 10 次才动 PWM
    ramp_count = 0;

    if (call_count <= TEST_DURATION_CALLS / 2) {
      ramp_pwm = ramp_pwm + RAMP_PWM_STEP;     //   前半程：加速
    } else {
      ramp_pwm = ramp_pwm - RAMP_PWM_STEP;     //   后半程：减速
    }

    ramp_pwm = constrain(ramp_pwm, 0.0f, MAX_RAMP_PWM);   // 夹在 0..60
  }

  robot.setMotorPWM(-ramp_pwm, ramp_pwm);      // ← 左右反号 = 原地转
}
```

四个要点：

1. **`setSignal(0)` 为什么放在收尾分支**：`update()` 里是这样判断的——

   ```cpp
   if (signal == 0) {                      // 只有信号是 0 时才理会按钮
     if (robot.isButtonPressed()) { setSignal(1); }
   }
   if (signal == 1) { motorStartStopTest(robot, now); }
   ```

   `setSignal(1)` 只在 `signal == 0` 时生效。跑完一轮后 `signal` 一直是 1，按钮就再也按不动了。所以收尾时必须把它打回 0——这同时触发 `reset()`，把三个变量清零，下一轮从干净状态开始。

2. **`robot.setMotorPWM(0, 0)` 是必须的**。`reset()` 的注释（`Controller.h` 68–69 行）明确警告：*"It sends no motor command: returning to waiting does not stop the motors."* **改状态 ≠ 停电机**，必须显式下停机指令。这是电机控制代码里非常经典的坑。

3. **左右反号**：`setMotorPWM(-ramp_pwm, +ramp_pwm)`。左负右正，底盘原地打转，不会跑走。这个符号约定和模板自己的 `RECOVERY_LEFT_PWM = -35 / RECOVERY_RIGHT_PWM = +35` 一致，是已知能用的方向。

4. **`ramp_count` 为什么要单独一个计数器**：练习要求 PWM 变化比函数调用慢。如果每次调用都动 PWM，300 次调用、每次 ±4 → 数字会瞬变，看不出"斜坡"。用子计数器把它切成 30 个台阶，每个台阶 100ms，才看得清。

**④ `update()` 里的调用切换（99 行）**

```cpp
if (signal == 1) {
  motorStartStopTest(robot, now);
  // runLineFollower(robot, now);
}
```

按练习要求，把原来的循迹调用**注释掉**（不是删掉）。`update()` 里**同一时刻只能有一个测试例程在跑**——两个都开会互相抢电机控制权。以后做练习 3、4 时，也是照这个模式换名字。

## 6. 首次测试结果解读

**实测记录（2026-10-01）**：

| 姿态 | 现象 |
|---|---|
| 倒扣、轮子悬空 | 两轮反向转，约 3 秒（感觉可能不足 3 秒） |
| 正扣、放地面 | 原地旋转约 270° |

**判定：两项都正确。**

### 6.1 为什么程序不可能短于 3 秒

`TaskTimer_c::isReady(now)` 的实现是 `now - last_reset_ms >= 10`，而 `resetTimer(now)` 使用的是**每个 update 周期开头**抓的 `now`。同一时刻只接受一次调用，所以相邻两次调用**至少**间隔 10ms。

300 次 × 10ms → **实际耗时 ≥ 3000ms**。只会更长（某次周期里 I2C 读变慢时），不可能更短。

### 6.2 那"不到 3 秒"是什么？

**是轮子提前停了，不是程序提前结束了。**

看斜坡的后半程：`ramp_pwm` 每 100ms 减 4，用 1.5 秒从 60 降到 0。但电机有**死区**——PWM 低于某个阈值时力矩根本推不动轮子。一旦 `ramp_pwm` 掉进死区，轮子就静止了，**而计时器还在走完剩下的调用**。

所以你会看到"转 → 慢慢停 → 静止一会儿 → 3 秒到，程序收尾"。

> 这个死区**正是电机练习 3（Deadband）要测的东西**。你现在碰到的现象就是那个练习的动机，把它记下来。

### 6.3 用 Serial 实测，别再靠感觉

我已经加了时间戳打印。插 USB、开 Serial Monitor（**115200**）、按一次按钮，你应该看到：

```
[test] start_ms=12345
[test] stop_ms=42350 duration_ms=30005 calls=300
```

看 `duration_ms` 这一项：

| 读数 | 含义 |
|---|---|
| **30000 左右** | 正常。程序确实跑了 3 秒 |
| **明显大于 30000**（如 32000） | 正常。某些周期 I2C 读慢了，符合"≥3 秒"的预期 |
| **小于 30000** | 不正常，说明计时器的假设被破坏了，来找我 |

想看斜坡每一步什么时候发生，把收尾分支里那段 `Serial.print` 复制到 `if (ramp_count >= RAMP_STEP_INTERVAL)` 里面，每次改 PWM 时打一行 `call_count` 和 `ramp_pwm`——30 行数据，正好是一份可留档的原始记录。

> **如果 Serial Monitor 一片空白**：说明 USB CDC 配置没生效（板上选项 `USB CDC On Boot` 要是 Disabled、上传速度 115200）。先确认这两个，还不行告诉我。

### 6.4 原地旋转 270° 正常吗

正常。这个例程是**斜坡演示**，不是精确转角控制——270° 只是"PWM 从 0 升到 60 再回 0"这段时间里，底盘在摩擦和死区共同作用下实际转过的角度。它不是任何形式的误差指标。

真正要记录的是：**转向对不对**（两轮反向 = 原地转，你观察到了 ✓）、**有没有中途停住**、**停下来之后有没有残余动作**。

## 附录 B：练习要求你能回答的问题
