## 3. 代码讲解

### 3.1 五个常量（`Controller.h`）

| 常量 | 值 | 含义 |
|---|---|---|
| `ENCODER_COUNTS_PER_REV` | 358.3 | 轮子整转一圈产生多少个计数 |
| `WHEEL_DIAMETER_MM` | 32.0 | 轮径（mm） |
| `SPEED_SAMPLE_INTERVAL` | 5 | 每 5 次 `update()` 采一次 → **50ms / 20Hz** |
| `SAMPLES_PER_TRIAL` | 200 | 一轮 200 个样本 → **10 秒** |
| `TEST_PWM` | 0.0 | 电机指令。**0 = 不供电，用手转** |

**358.3 是怎么来的**（Pololu 官方数据）：编码器在**电机轴**上每转一圈给 12 个计数，电机经过 **29.86:1** 减速箱才到轮子，所以 `12 × 29.86 = 358.3` 计数／轮子一圈。
> 这是 **Standard Edition** 的数字。Turtle Edition 是 75.81:1 → 909.7。课程页面写的就是 358.3，所以你是 Standard。后面对标 odometry 练习时会标定你这个机器人**实际**的有效轮径，别把 32.0 当真理。

由此得到两个换算因子：
- 轮子周长 = π × 32 = **100.53 mm**
- 每计数 = 100.53 / 358.3 = **0.2806 mm**
- 每毫米 = **3.564 计数**

### 3.2 为什么必须降频（练习的核心洞察）

练习页面给了一个算术：**机器人以 10 mm/s 前进时，100Hz 采样每个间隔只有 0.36 个计数。**

编码器计数是 `int32_t`（整数），**0.36 存不下，会被丢掉**——直接变 0。于是慢速运动在数据里完全消失。

| 采样间隔 | 采样率 | 10 mm/s 时每样本计数 |
|---|---|---|
| 10 ms | 100 Hz | **0.36** ← 丢光 |
| 50 ms | 20 Hz | 1.78 |
| 100 ms | 10 Hz | 3.56 |

我选了 50ms（`SPEED_SAMPLE_INTERVAL = 5`）。想要更稳就调大这个数——**代价是响应变慢**，快速变化会被抹平。这个取舍练习的 AI 路线专门要求你能解释。

> 注意：`speed_sample_count` 就是练习 1 里 `ramp_count` 的同一个套路——**子计数器分频**，非阻塞，一行 `delay()` 都没有。

### 3.3 `measureWheelSpeed()` 逐段

```cpp
// ① 一轮跑完 200 个样本就收工
if (sample_num >= SAMPLES_PER_TRIAL) {
  robot.setMotorPWM(0, 0);      // 显式停机
  setSignal(0);                 // 解除信号，允许再按按钮跑下一轮
  return;
}

// ② 按 TEST_PWM 驱动电机（0 就是不驱动）
robot.setMotorPWM(TEST_PWM, TEST_PWM);

// ③ 分频：没到第 5 次就返回
speed_sample_count = speed_sample_count + 1;
if (speed_sample_count < SPEED_SAMPLE_INTERVAL) { return; }
speed_sample_count = 0;

// ④ 读缓存快照（左右来自同一瞬间）
int32_t count_left  = robot.getLeftEncoderCount();
int32_t count_right = robot.getRightEncoderCount();

// ⑤ 本轮第一次采样：只建立基准线，不算速度
if (!speed_baseline_set) {
  last_count_left = count_left;
  last_count_right = count_right;
  last_time_ms = now;
  speed_baseline_set = true;
  trial_num = trial_num + 1;    // 新的一轮，编号 +1
  sample_num = 0;
  return;
}

// ⑥ 实测间隔（不是假定 10ms）
float delta_ms = (float)(now - last_time_ms);

// ⑦ 防除零——练习明确要求
if (delta_ms > 1.0f) {
  float delta_left  = (float)(count_left  - last_count_left);   // 当前 - 上次
  float delta_right = (float)(count_right - last_count_right);
  speed_left_cps  = delta_left  / delta_ms * 1000.0f;           // 计数/秒
  speed_right_cps = delta_right / delta_ms * 1000.0f;
  float mm_per_count = (PI * WHEEL_DIAMETER_MM) / ENCODER_COUNTS_PER_REV;
  speed_left_mm_s  = speed_left_cps  * mm_per_count;            // 换成 mm/s
  speed_right_mm_s = speed_right_cps * mm_per_count;
}

// ⑧ 本次快照成为下一次的参照
last_count_left = count_left;
last_count_right = count_right;
last_time_ms = now;

// ⑨ 打印一行 CSV
...
sample_num = sample_num + 1;
```

**四个刻意的设计决定，都要能讲出来：**

1. **⑤ 为什么要基准线**：开机时 `last_count_left` 是 0，但编码器计数值可能已经是几千。如果不先建立基准，第一个样本会算出"开机以来走了多远除以 50ms"这种天文数字。

2. **④ 为什么不在函数里再调 `getEncoders()`**：`getEncoders()` 是**刷新缓存**的动作，`getLeftEncoderCount()` 只是**读缓存**。`update()` 每个周期已经刷新过一次了。如果在这里再刷一次，左右轮的读数会来自**两个不同瞬间**，差分会引入误差。练习的 AI 路线专门问这个："Which operation refreshes the cache, and which merely reads it?"

   > 副作用：如果 `update()` 里那次读取**失败**了，缓存里留的是旧值——表现为"计数没变"，而不是报错。这是个静默故障，心里要有数。

3. **⑦ 符号约定**：我用的是**当前 − 上次**，所以**前进 = 正速度**。Colab notebook 里 pandas 的 `.diff()` 也是"当前 − 上次"，**两边一致**。
   > 练习页面给的示例代码写的是 `last_count_left - robot.getLeftEncoderCount()`，**方向相反**。两种都行，但必须选定一种，并且物理验证。练习第 8 步问的就是这个："Does a positive speed correspond to a forward movement of the robot?"

4. **⑨ 表头只打一次**：`csv_header_done` 在**构造函数**里置 false，`reset()` 故意不碰它。因为 `reset()` 每轮结束都会被调用——如果它清零这个标志，CSV 中间就会插进表头，整个文件就没法解析了。

## 4. CSV 格式

```
trial_num,sample_num,timestamp_ms,requested_left_pwm,requested_right_pwm,left_encoder_count,right_encoder_count,left_speed_mm_s,right_speed_mm_s
```

- **前 7 列是 notebook 明确要求的**，一列都不能少、顺序不能变
- 后 2 列（mm/s）是我加的，对应练习"换成有意义单位"那条要求。**notebook 不读它们**，纯给你报告用，顺手还能拿来交叉验证（见 §7）
- 计数是**累计值**不是增量——notebook 自己会做差分
- 一轮 200 行，10 秒

`update()` 里原本每 50ms 无条件打一行 **14 列**的通用遥测（timestamp, x, y, theta, pwm, 计数, DN1–DN5, signal）。它和 9 列的测量行**交织在一起**，CSV 就没法解析了。

课程练习 2 第 7 步专门点名了这件事：

> *"If you do not comment out the line `publishTelemetry(robot, server, now);` in `update(...)`, you will see your speed measurement reported alongside the general data from the robot published to the simulator."*

我已经把它注释掉了（`Controller.cpp` 里那一行）。**想恢复 Digital Twin 的实时数据流时就取消注释**——但那期间就别抓 CSV 了。

### 手转那轮（`TEST_PWM = 0`）长这样

```
trial_num,sample_num,timestamp_ms,requested_left_pwm,requested_right_pwm,left_encoder_count,right_encoder_count,left_speed_mm_s,right_speed_mm_s
1,0,12395,0,0,1518,1498,56.115,0.000

1,2,12495,0,0,1527,1498,0.000,0.000
1,3,12545,0,0,1535,1498,44.892,0.000
```

> ⚠️ **上面的数字是我编的示意**，用来说明格式和"自洽关系"，不是你机器人会给出的值。每一行的自洽关系是：`(本行计数 − 上行计数) ÷ 0.05 × 0.2806 = 本行 mm/s`。你可以拿这个式子验算任意一行。

**手转会呈现的特征**：
- 数值**抖**——手转不均匀，10/9/11 个计数跳来跳去
- **经常归零**——手停下来或转得太慢时
- **换手方向，符号翻转**
- **只动一个轮子时，另一个轮子的两列全 0**

### 通电那轮的特征

- 开头几个样本**数值小**（电机在加速）
- 然后**快速拉平成一个平台**——这是练习页原话 "you should be able to observe relatively stable speed estimation values"
- 手转的抖动比通电**大得多**，通电后曲线明显更平
- 左右两个平台**不会完全相等**（这就是后面练习 4–6 要量化的不对称）

### 两个你能自己算出来的数

**① 量化台阶 = 5.6 mm/s**

50ms 采样间隔下，**1 个计数** = `1 ÷ 0.05 = 20 计数/s` = `20 × 0.2806` = **5.61 mm/s**。

也就是说：
- 低于 **5.6 mm/s** 的运动，读数就是 **0**（整数量化吃掉了）
- 读数实际上是 5.6 的整数倍跳变

对比一下 10ms 采样的台阶是 **28 mm/s**——这就是练习要求你降频的**量化收益**，可以在报告里写。

**② 量级锚点**

课程 notebook 的合成示例用的是 **610 counts/s**。换算：`610 × 0.2806 = 171 mm/s`，约 **1.7 圈/秒**。

> 课程明确说这个数**不是**你该复现的结果。但它给了你个数量级：**通电后正常读数应该在几十到几百 mm/s 这个范围**，不是个位数也不是几万。

### 故障对照表

| 你看到的 | 最可能的原因 |
|---|---|
| **串口完全没输出** | ① 串口被 Arduino IDE 的 Serial Monitor 占着（同一端口不能两开）② 板子没在跑新代码 ③ USB-C 线只供电不传数据 ④ `CDCOnBoot` 被改成了 `cdc`（见 §6） |
| 有数据但**没有表头行** | 板子没复位就接着上次跑；拔插 USB 重来 |
| **计数和速度全是 0**（通电也不动） | ①`TEST_PWM` 还是 0 ②电机没转 ③编码器读数一直失败 |
| **计数在变但速度列恒 0** | 间隔没超过 1ms 的防除零保护被触发（不该发生，来问我） |
| 速度是**个位数乱跳** | 转得太慢，撞上 5.6 mm/s 的量化台阶——不是 bug |
| 速度是**几万这样的大数** | 基准线没建立成功（第一行就异常），来问我 |
| **符号和物理方向相反** | 约定问题，不是错误——但要改成一致的，别带着走 |
| 表头**出现在 CSV 中间** | 不该发生（`csv_header_done` 我特意没放进 `reset()`），来问我 |
| 计数**偶尔不连续跳** | I2C 读偶发失败，缓存留旧值。偶发可容忍，频繁就是硬件/线缆问题 |
